# Профили: несколько человек в одном SEL

## Зачем
Попросил тренер: он ведёт клиентов и хочет в SEL видеть их прогресс — прежде всего фото формы по сериям, а дальше и
питание (FatSecret клиента). Один профиль — один человек. Всё приложение (сводка, питание, тренировки, восстановление,
фото, настройки, цели, план, БАДы, алкоголь, подключения FatSecret и Whoop) работает внутри текущего профиля.

Это первая из двух частей. Вторая — отдельным дизайном: **подключение FatSecret по внешнему коду** (тренер даёт
клиенту ссылку, клиент входит на fatsecret.com у себя, присылает код, тренер вставляет его в SEL). Основа для неё
уже есть: запасной режим `oob` в `main.js` и поле «Код со страницы FatSecret» в «Настройках».

## Цели
- Папка данных — корень с профилями: `data/profiles/<id>/` — у каждого свои CSV, фото, токены, `sync.json`, `docs/`.
- Первый запуск: после выбора папки — «Как назвать профиль?»; данные кладутся в него.
- Обновление с 1.x: тот же вопрос, и **нынешние данные один раз переносятся в этот профиль**.
- Переключение профиля из меню на любой странице; создание, переименование, удаление.
- Вес вручную при загрузке фото (у клиентов без FatSecret веса иначе нет).

## Не цели
- Подключение FatSecret по внешнему коду — часть 2.
- Сравнение разных людей между собой (рядом, на одном экране).
- Обновление всех профилей сразу: обновляется только текущий.
- Whoop для клиента — только как сейчас: клиент сам входит в окне SEL на этом компьютере.
- Выгрузка/передача профиля, общий доступ, пароли на профили.

## Анти-цели
- Потерять или испортить данные при переносе (прерванный перенос, падение посреди).
- Смешать данные людей: фото, CSV или токены одного профиля оказываются в другом (например, обновление,
  начатое до переключения, дописывает в новый профиль).
- Показать токены и ключи (как и сейчас).
- Два устройства хранения «у первого — корень, у остальных — профиль»: устройство одно для всех.

## Ограничения
- Версия **2.0.0**: перенос папки данных необратим, 1.x после него данных не найдёт (SemVer X — см. CLAUDE.md).
- Схема CSV не меняется (`desktop/schema.json`), формат каждого файла — прежний, меняется только где лежат.
- Писать CSV — только через `store.js`; страницы ничего не грузят наружу (CSP) — как сейчас.
- Mac и Windows; Node без зависимостей в `scripts/`.

## Подходы (выбран А)
- **А. Профиль = отдельная папка данных `data/profiles/<id>/`** — выбран пользователем. Весь код уже завязан на одну
  переменную `DATA` в `main.js`; профиль = другое значение `DATA`, переключение = смена `DATA` + перезагрузка окна.
  Страницы и расчёты не меняются. Цена — перенос данных при обновлении и версия 2.0.0.
- Б. Владелец остаётся в корне `data/`, клиенты — в `data/profiles/<id>/`. Без переноса (1.4), но два устройства
  навсегда; против просьбы пользователя «складывать в профиль с первого запуска».
- В. Одна папка, колонка «профиль» в каждом CSV и метка у фото — отвергнут: перемешивает синхронизацию и все таблицы,
  портит шаблоны выравнивания фото (медианы по всем снимкам папки).

## Как устроено

### Папка данных
```
<dataDir>/                     ← путь из config.json → dataDir (как сейчас; по умолчанию Документы/SEL/data)
  README.md                    ← про корень: что такое профили, где что лежит (пишет приложение)
  secrets/                     ← только ключи приложений: fatsecret_app.json, whoop_app.json (для сборки/разработки, keys.js)
  profiles/
    <id>/
      profile.json             ← {"name": "Александр", "created": "2026-11-23"} (пишет приложение)
      README.md                ← нынешний README папки данных (desktop/data_readme.md) — про файлы профиля
      *.csv · sync.json · photos/ · docs/
      secrets/                 ← токены этого человека: fatsecret.json, whoop.json
  <любые незнакомые файлы>      ← не трогаем
```
- `<id>` — латиница из имени при создании (транслитерация, нижний регистр, `-`; занято — `-2`, `-3`…; пустое — `profile`).
  При переименовании **id не меняется**, меняется только `name` в `profile.json`.
- Текущий профиль — `config.json` → `profile: "<id>"` (рядом с `dataDir`). Нет или профиль пропал — первый по имени.
- Где лежат файлы внутри профиля — ровно как раньше в корне; `store.js`, `photosfs.js`, `updater.js` и т. д.
  получают папку профиля вместо корня.

### Перенос с 1.x (один раз)
Признак: в корне `dataDir` есть CSV из схемы, а `profiles/` нет или пуста.
1. Окно показывает экран «Как назвать профиль?» с пояснением «ваши данные перенесём в этот профиль». До ответа
   ничего не двигается; приложение данные не показывает.
2. После ответа: создать `profiles/<id>/`, записать `profile.json` с полем `migrating: true`.
3. Переместить (rename, не копирование) в профиль то, что приложение знает: CSV из схемы, `sync.json`, `photos/`,
   `docs/`, `README.md`, а из `secrets/` — `fatsecret.json`, `whoop.json`. Ключи приложений (`*_app.json`) остаются
   в корневом `secrets/`. Если `fatsecret.json` содержит consumer-поля (старая раскладка, keys.js), а
   `secrets/fatsecret_app.json` нет — сначала записать его из этих полей.
4. Убрать `migrating` из `profile.json`, записать `profile` в `config.json`, написать корневой README.
- Прерванный перенос (есть профиль с `migrating: true`) — при запуске продолжить с шага 3 без вопросов
  (перемещение уже переехавшего — пропуск).
- Незнакомые файлы и папки корня не трогаем; `.DS_Store` — тоже.
- Правило о ключах приложений в старом `fatsecret.json` — так же и для `whoop.json` (client_id/secret/redirect_uri →
  корневой `secrets/whoop_app.json`, если его нет).
- **Старые данные в корне при уже существующих профилях** (запустили 1.x после переноса — она создаст пустые CSV;
  вернули копию из Time Machine): пустые CSV из схемы (только заголовок) — не трогать и не спрашивать. Если хотя бы
  в одном корневом CSV есть строки — при запуске сообщение «В папке данных, вне профилей, лежат старые данные — SEL
  их не показывает» с кнопками «Перенести в новый профиль» (экран имени → те же шаги переноса) и «Оставить как есть»
  (больше не спрашивать до изменения этих файлов). *(решение Claude)*
- `datadir.fromPicked` и «Сменить папку…» узнают корень с `profiles/` (как сейчас узнают папку с CSV).

### Первый запуск (новичок)
Выбор папки — как сейчас. Если в ней нет профилей и нет старых CSV — тот же экран «Как назвать профиль?»
(без слов про перенос) → профиль создаётся пустым → сводка с «Подключите FatSecret или Whoop».
Если выбрана папка, где профили уже есть (переустановка) — не спрашивать, открыть первый.

### Экран «Как назвать профиль?»
Страница приложения (portal, как остальные; не диалог — в диалогах Electron нет поля ввода). Одно поле «Имя»,
кнопка «Создать». Пустое имя нельзя; длина — до 40 символов. Меню на этом экране нет.

### Переключение
- В меню (nav.js) справа — имя текущего профиля ▾. Список: все профили по имени, текущий отмечен; внизу
  «Новый профиль…» и «Профили…» (→ «Настройки»). Если профиль один — то же меню (чтобы было где создать второй).
- Переключать нельзя, пока идёт обновление, вход в FatSecret/Whoop или запись фото (загрузка, пересборка,
  удаление): пункты неактивны, подсказка, чего ждём. *(решение Claude)*
- **Окна входа FatSecret и Whoop** (сессии `fatsecret-login`, `whoop-login` — в памяти, общие на весь запуск):
  перед каждым входом очищать их куки и хранилище — иначе второй человек автоматически войдёт под аккаунтом первого.
  *(решение Claude)*
- Выбор профиля → `main.js`: сменить `DATA`, сохранить `profile` в `config.json`, сбросить состояние,
  привязанное к профилю (ожидающий вход FatSecret `pending`, статусы `updater.status`), перезагрузить окно на ту же
  страницу и запустить обновление этого профиля, как при старте.
- Окно «Что нового» не зависит от профиля (как сейчас — по `config.json`).

### «Настройки» → карточка «Профили» (первая на странице)
- Список: имя, «текущий», кнопки «Переименовать», «Удалить»; форма «Новый профиль» (имя → создать и переключиться).
- Переименовать — меняет `name`; папку не трогает.
- Удалить — подтверждение: «Удалить профиль „Иван“? Папка с его данными и фото (N снимков) уйдёт в Корзину».
  В Корзину (`shell.trashItem`), не насовсем. Последний профиль удалить нельзя. Удалили текущий — переключиться
  на первый оставшийся.

### Фото
- `app://h/data/photos/…` и `health:photos` указывают на `photos/` текущего профиля — страница «Фото» не знает
  о профилях. Шаблоны выравнивания — по снимкам профиля (один человек), как сейчас.
- **Вес вручную — во всех профилях** (решение пользователя). В окне загрузки у каждой серии рядом с датой — «Вес, кг»
  (необязательно; если в `body.csv` **на дату серии** вес есть — подставлен). Сохранить → `weight_kg` строки
  `body.csv` профиля **на дату серии** через `store.upsert`, **без пометки** (`note` не пишем, прежнюю не трогаем).
  Под снимком в сравнении вес (сейчас — ближайшее взвешивание в 14 днях, `nearestWeight`) кликабелен — поле «Вес на
  дату серии»: пишет/заменяет вес на дату серии, чужие даты не трогает; после этого под фото — вес на эту дату.
  *(решение Claude)*
- Ручной вес и вес FatSecret на одну дату — **побеждает последний записавший** (решение пользователя): ручной правит
  вес FatSecret, следующая догрузка FatSecret на эту дату — ручной. `fatsecret.js` не меняем.

### Скрипты и проверки
- `scripts/csv.js` — работает с текущим профилем; `--profile <id>` — с другим; `dir` печатает папку профиля и список
  профилей.
- `scripts/public_check.js` и тест «настоящая папка данных» — по всем профилям и корневому `secrets/`.
- Сборка берёт ключи приложений из корневого `secrets/` (keys.js) — как сейчас, путь тот же.
- Проверочный запуск `HEALTH_DOCUMENTS=…` — папка с профилями; профиль — `HEALTH_PROFILE=<id>` или первый.
